● Your code is a small authenticated Next.js app. Right now it does one complete flow: connect to PostgreSQL with Prisma, authenticate users with email/password, redirect unauthenticated users to /login, and
  let authenticated users enter the home page and log out.

  The project structure

  There are really two levels:

   - Repo root: project docs like README.md and docs/architecture.md
   - web/: the actual application

  How the app works as a whole

  The runtime flow is:

   1. A user opens /
   2. The home page checks whether there is a session
   3. If there is no session, Next.js redirects to /login
   4. The login form sends email/password to NextAuth
   5. NextAuth looks up the user in PostgreSQL through Prisma
   6. It compares the entered password with the stored hashed password using bcrypt
   7. If valid, a session is created
   8. The user is sent back to /
   9. The home page now renders and shows the user's name/email
   10. Clicking Logout clears the session and sends the user back to /login

  app/api/auth/[...nextauth]/route.ts

  This is the authentication backend. It is the core of login.

  What it contains:

   - NextAuth
   - CredentialsProvider
   - bcrypt.compare
   - prisma

  authOptions

  This object defines how authentication works.

  It uses a credentials provider, meaning you are not using Google/GitHub login. You are using your own database and your own email/password check.

  authorize(credentials)

  This is the critical function.

  It does:

   1. Validate that email and password were provided
   2. Query the database: prisma.user.findUnique({ where: { email: credentials.email } })
   3. If no user exists, throw an error
   4. Compare the plain password from the form against user.passwordHash
   5. If the password is wrong, throw an error
   6. If correct, return a user object with:
    - id
    - email
    - name
    - role

  That returned object is what NextAuth uses to create the session.

  handler

   const handler = NextAuth(authOptions);
   export { handler as GET, handler as POST };

  This exposes the auth route to both GET and POST requests in the App Router style.

  Why authOptions is exported

  Because other server-side files reuse it with:

   getServerSession(authOptions)

  That way, your pages and your auth route use the same exact auth configuration.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  app/login/page.tsx

  This is the server-rendered login page.

  What it does:

   - Calls getServerSession(authOptions)
   - If the user is already logged in, it redirects to /
   - Otherwise, it renders the login UI container and includes LoginForm

  Why this matters:

   - Logged-in users should not see the login page again
   - This check happens on the server before rendering

  So this file is mostly routing logic + page shell.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  app/login/login-form.tsx

  This is the interactive client-side login form.

  It is a client component because it uses:

   - React state
   - browser navigation
   - signIn() from next-auth/react

  Local state

  It stores:

   - email
   - password
   - isPending
   - error

  handleSubmit

  This function runs when the form is submitted.

  It does:

   1. Prevent the browser's default form submission
   2. Clear old errors
   3. Set loading state
   4. Call: signIn("credentials", {
      email,
      password,
      redirect: false,
    })
   5. Stop loading state
   6. If login failed, show "Invalid email or password"
   7. If login succeeded:
    - router.push("/")
    - router.refresh()

  Why redirect: false matters:

   - You are controlling the result manually
   - That lets you show inline errors instead of letting auth immediately redirect the browser

  So this file is the UI bridge between the user and your auth backend.

  app/page.tsx

  What it does:

   - If there is no session, redirects to /login

  This is your current route protection strategy:

  That means the page itself refuses to render unless the user is authenticated.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  lib/prisma.ts

  This is your shared Prisma client setup.

  It imports:

   - PrismaClient from the generated client
   - PrismaPg from @prisma/adapter-pg

  Then it creates a Prisma client using DATABASE_URL.

  Why the globalThis trick exists

  In development, Next.js can reload modules many times. If you create a new Prisma client on every reload, you can end up with too many DB connections.

  So you do this:

   - check if globalForPrisma.prisma already exists
   - reuse it if it does
   - otherwise create a new one
   - in non-production, cache it globally

  That is the standard pattern for keeping Prisma stable in a hot-reloading app.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  prisma/schema.prisma

  This defines your database schema.

  Generator

   generator client {
     provider = "prisma-client"
     output   = "../generated/prisma"
   }

  This tells Prisma to generate the client code into generated/prisma.

  Datasource

   datasource db {
     provider = "postgresql"
   }

  This says the DB is PostgreSQL.

  Enum

   enum UserRole {
     ADMIN
     TESTER
   }

  This gives users a role system, even though the role is not heavily used yet.

  Model

   model User {
     id           String   @id @default(cuid())
     name         String?
     email        String   @unique
     passwordHash String
     role         UserRole @default(TESTER)
     createdAt    DateTime @default(now())
     updatedAt    DateTime @updatedAt
   }

  This means:

   - every user has a unique email
   - passwords are stored as hashes, not plain text
   - users get a role
   - timestamps are automatically managed

  This is the entire data model currently implemented.

  prisma/seed.ts

  This creates an initial admin user.

  What it does:

   1. Imports the shared Prisma client
   2. Uses bcrypt.hash("admin123", 10) to hash the password
   3. Runs prisma.user.upsert(...)

  upsert means:

   - if the user exists, update it
   - if not, create it

  That makes the seed script safe to run multiple times.

  It seeds:

   - email: admin@incidenthub.local
   - name: IncidentHub Admin
   - role: ADMIN

  This is how your login flow has a known working user.

  The most important design choices in your code

   1. Server-side route protection
  You protect pages by calling getServerSession(authOptions) inside server components.
   2. Credentials auth with your own DB
  You control authentication yourself instead of using OAuth.
   3. Hashed passwords
  Passwords are checked securely with bcrypt.
   4. Prisma singleton pattern
  Prevents extra DB clients during development.
   5. App Router split between server and client components  
    - server components for session checks and redirects
    - client components for interactive auth actions like signIn and signOut
